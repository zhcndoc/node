# 面向首次贡献者的指南和常见问题

欢迎来到 Node.js 项目！本指南是对
[通用贡献指南](../../CONTRIBUTING.md)
和 [拉取请求指南](./pull-requests.md) 的补充，重点在于
澄清首次贡献者的流程。

## 开始之前

在为项目做贡献之前，请阅读并理解 [行为准则](./code-of-conduct.md)。

## 从问题开始入手

如果你的第一次贡献并不是由你已经遇到的某个问题所驱动，而只是想帮忙，
你可以通过浏览 [问题跟踪器](https://github.com/nodejs/node/issues) 来寻找可处理的问题。
按 `good first issue` 标签筛选问题，可以找到适合首次贡献者的问题。`help wanted`
用于跟踪那些需要志愿者帮助、但由于复杂度较高或需要特定领域专业知识而可能更具挑战性的问题。

如果你的第一次贡献是由你已经遇到的某个问题所驱动，但你拟议的更改
很复杂、引入了新功能、破坏了向后兼容性，或者需要进行重大重构，
那么在开始处理实现细节之前，先开一个 issue 来讨论该更改或其设计是否可接受，会很有帮助。
你可以在发送 pull request 之前开这个 issue，
也可以和 pull request 一起提交（在这种情况下，最好将 pull request 保持为草稿模式）。

像明显的 bug 修复或小规模重构这类直接、无争议的更改，通常不需要通过单独的 issue
进行讨论，可以直接作为 pull request 提交。

### 在 issue 中沟通

Node.js 是一个由志愿者推动的社区项目。没有项目经理会将 issue 分配给某个人。
在 GitHub 上不需要请求分配。
相反，贡献者通常通过评论来沟通进展。

请避免只在 issue 下留下一条“接手”评论，却没有后续跟进。如果问题很直接，
你可以立即开始处理它。如果任务更复杂，在你有重要发现或在准备好 pull request 之前
遇到阻碍时，在 issue 中留下更新是可以的，这样可以避免其他贡献者重复劳动。

避免同时挑选多个 issue，尤其是同类型或同领域的 issue。
最好专注于一个 issue，并将其完成后再去挑选另一个。

在沟通时，要注意评论的长度。长评论可能难以阅读，
并可能让其他人不愿参与讨论。请避免粘贴大段代码、日志或由工具生成的文本。
如有必要，可以使用 `<details>` 标签将其折叠到可展开的部分中，以使讨论更易读。

## 初次贡献时不要做什么

**不要自动化你的首次贡献**。在这个项目中，任何自动化都必须
经过授权并被明确跟踪。如果你有关于自动化的想法，请先开一个
issue 与其他贡献者讨论。

**不要在首次贡献时提交大型拉取请求**。Node.js 通过一种
[在协作者之间寻求共识的流程](./collaborator-guide.md#consensus-seeking)来做出
技术决策，并会额外考虑社区反馈。即使对有经验的贡献者来说，
推动复杂变更通过这个流程也可能很困难，而对首次贡献者来说则可能令人沮丧。
最好从更小、更聚焦的拉取请求开始，处理已知问题，这样你可以先熟悉
协作流程。当你在积累一些经验后不得不提交大型拉取请求时，
请务必遵循[大型拉取请求指南](./large-pull-requests.md)。

**在第一个 Pull Request 还未被批准之前，不要开启新的 Pull Request**。
这会给别人留下你在淹没项目的第一印象。
第一次没有把所有事情都做对是可以接受的，但如果你开启 PR 的速度
快于它们被审查的速度，你就是在浪费改进的机会，并且可能会让
你自己和审查者都被通知信息淹没。

## 通过拉取请求审查流程

当你准备提交拉取请求时，请查看[拉取请求指南](./pull-requests.md)，
以了解有关审查流程的技术操作说明和解释。

首次贡献者应注意，该项目使用
[开发者原创声明（DCO）](https://developercertificate.org/)来管理
贡献的版权。请务必
[为你的提交签署确认](./pull-requests.md#step-4-commit)（例如，使用 `git commit -s`），
否则它们将无法被合并。

## 关于拉取请求的常见问题

### Q: 为什么我的拉取请求没有得到审查？

在 Node.js 中，能够批准拉取请求合并的人群是
[协作者](../../GOVERNANCE.md#collaborators)。虽然协作者很多，但他们都是时间有限的志愿者，
并不总是会关注新的拉取请求，因为项目很大，通知量也可能让人应接不暇。

当你的拉取请求没有得到关注时，你可以

1. 尝试向在原始 issue 中表现出兴趣的协作者发消息提醒。
2. 尝试在
   [OpenJS Slack 的 #node-core 频道](https://openjs-foundation.slack.com/archives/C019Y2T6STH)中寻求帮助。

**请保持耐心，并尊重审查者作为志愿者投入的时间**。如果你礼貌待人，并尊重他们自愿进行审查的付出，人们通常会更愿意提供帮助。

### Q: 我的拉取请求上有一些审查评论。我应该如何更新我的拉取请求来回应这些意见？

如果审查评论是使用 GitHub 的建议功能留下的，你可以直接在 GitHub UI 中应用这些建议，
并将更改提交到你的分支。否则，你可以向拉取请求分支推送新的提交。
技术操作方法请参见[拉取请求指南](./pull-requests.md#step-9-discuss-and-update)。

在你推送新提交后，即使之前的提交已经被批准，你仍然需要针对最后这些提交获得新的批准。

同一个拉取请求中的提交通常会在合并前压缩成一个提交，除非有充分理由保留它们分开——在这种情况下，请与你的审查者协调。
需要保留为独立提交的内容必须各自单独通过所有测试，并遵循[提交消息指南](./pull-requests.md#commit-message-guidelines)。

提交压缩通常由自动化处理。原本打算在压缩时被合并掉的提交，不需要遵循提交消息指南——只有那些在压缩后仍会保留提交消息的提交才需要遵循。
如果你的提交已经获得批准并且 CI 已通过，你无需担心自己去压缩它们——自动化会在落地时处理。

自动化使用 `git rebase --autosquash`，它可以识别由 `git commit` 命令的
[`--fixup`](https://git-scm.com/docs/git-commit#Documentation/git-commit.txt---fixupamendrewordcommit) 和
[`--squash`](https://git-scm.com/docs/git-commit#Documentation/git-commit.txt---squashcommit) 标志留下的提示。
你可以在向拉取请求添加新提交时使用这些标志，以表明应如何进行压缩。

### Q: 我更新了我的拉取请求，但没有收到回应。我该怎么办？

当你更新拉取请求时，审查者未必会自动收到通知，这取决于他们如何配置通知设置。
他们也可能错过通知，或者当时确实没有足够的时间以志愿者身份参与项目。
你可以再尝试提醒他们一次，让他们知道有更新。请保持耐心，不要用过多提醒轰炸他们。
作为参考，审查者对拉取请求做出回应的一般预期周期大约是
[48 小时到 7 天](./collaborator-guide.md#code-reviews)。

### Q: 我的拉取请求有合并冲突。我该怎么办？

当目标分支更新后，拉取请求中出现了合并冲突，你需要将你的拉取请求分支 rebase 到目标分支最新版本之上，
并在本地解决冲突，然后强制推送更新后的分支到你的 fork。
技术操作方法请参见[拉取请求指南](./pull-requests.md#step-9-discuss-and-update)。
rebase 之后，你还需要审查者给出新的批准。

**不要使用 GitHub 网页界面来解决合并冲突**。它创建的合并提交可能会导致 CI 出现问题。

### Q: 我的拉取请求需要通过哪些 CI 检查？

Node.js 使用两个 CI 系统：[Jenkins](https://ci.nodejs.org/) 和 GitHub Actions。Jenkins 是用于测试拉取请求的主要
CI 系统，而 GitHub Actions 用于快速检查和额外验证。仅涉及文档的拉取请求只需要通过 GitHub Actions
检查。凡是涉及文档以外内容的拉取请求都会被标记为 `needs-ci`，并且在合并前需要先运行 Jenkins CI。

### Q: 我如何触发 CI 运行？

由于 GitHub Actions 工作流可以访问敏感令牌，你在仓库中的第一个拉取请求需要协作者显式批准该工作流运行。
一旦你有一个拉取请求被合并，之后的拉取请求就会自动触发 GitHub Actions，而不需要批准。

出于类似的安全考虑，Jenkins CI 运行只能由有权限添加 `request-ci` 标签的协作者和 triager 触发。
但由于 Jenkins CI 需要测试大量平台和配置组合，而且基础设施资源有限，Jenkins CI 运行始终必须由人工触发，
不会自动运行。当你的拉取请求准备好进行 CI 测试时，你需要向协作者或 triager 寻求帮助来触发 Jenkins CI 运行。

志愿者需要花时间确认拉取请求不包含恶意代码后，才会批准 CI 运行。与审查过程类似，当你请求帮助触发 CI 运行时，
请保持耐心并尊重志愿者的时间，这有助于建立信任，使未来的贡献过程更顺畅。

### Q: CI 运行显示了一些看起来与我的更改无关的失败。我该怎么办？

Node.js 的 CI 已知存在不稳定性。请查阅
[reliability 仓库](https://github.com/nodejs/reliability/issues)中的每日报告，看看相同的失败是否也出现在其他拉取请求中——
如果是，那它们很可能与你的更改无关。在这种情况下，你可以忽略这些失败，并再次寻求帮助以重新触发 CI 运行——
这些失败通常是间歇性的，会在下一次运行中消失。

提示：这些不稳定问题长期困扰着项目，因为没有足够的志愿者来修复它们。如果你有时间并且感兴趣，
可以尝试志愿修复你有把握解决的那些问题！有关如何开始的更多细节，请参见
[reliability 仓库 README](https://github.com/nodejs/reliability#protocols-in-improving-ci-reliability)。

### Q: 我的拉取请求已经有足够的批准并且通过了 CI，但仍然没有合并。我该怎么办？

拉取请求需要由协作者或 triager 合并（通常是通过添加 `commit-queue` 标签）。
[commit queue 自动化](../../.github/workflows/commit-queue.yml)会在合并前验证拉取请求是否满足所有要求，
但是否触发 commit queue 仍然需要人工判断，并且取决于志愿者。
你可以像请求审查和触发 CI 运行那样，在拉取请求中或 Slack 频道里寻求帮助。

### Q: 有评论说我的拉取请求已经落地了，但我看到的却是我的拉取请求被关闭了，这是怎么回事？

在这个项目中，拉取请求通常通过
[commit queue](../../.github/workflows/commit-queue.yml) 来合并，以便用必要的元数据修正提交，
而不是通过 GitHub UI。有时自动化或执行合并的协作者会以一种让 GitHub 识别为已合并的方式更新分支，
并显示紫色的“merged”状态，但有时并不是这样。
只要你看到一条评论说你的拉取请求已经落地，并且这些提交确实出现在拉取请求的目标分支中，就不用担心，
这意味着更改实际上已经合并，无论 GitHub 显示什么。

### Q: 我的更改什么时候会发布？

如果拉取请求不是 `semver-major`，合并到 `main` 分支的提交通常会先在下一个 “Current” 版本中发布。
在 “Current” 版本中至少停留两周后，非 `semver-major` 的更改才有资格被纳入下一个 “LTS” 版本。
“Current” 和 “LTS” 版本遵循的时间表记录在
[Release Working Group 的置顶 issue](https://github.com/nodejs/Release/issues) 中。

如果更改被标记为 `dont-land-*`，它会在指定分支中被延后发布，直到该标签被移除。

如果更改被标记为 `semver-major`，它不会被包含在下一个 “Current” 版本中。
相反，它需要等待从 `main` 分支切出的下一个大版本，才会被包含进某个发布中。
这可能需要数月，具体取决于拉取请求何时被合并。

`main` 上的提交会在发布前使用 `git cherry-pick` 回移植到发布预备分支。
请参见[回移植指南](./backporting-to-release-lines.md)。这个过程通常由 Release Working Group 的志愿者执行，
但其他志愿者也可以帮忙。如果你的更改在回移植过程中没有按预期推进，你可以在 Slack 频道中寻求帮助，
看看是否由你自己来志愿进行回移植会有帮助。

### Q: 有人在我的拉取请求里评论说这个更改不能干净地落到某个发布分支上，我该怎么办？

当志愿者将你的提交 cherry-pick 到发布分支时，如果出现 git 冲突，或者该更改导致测试失败，
而志愿者无法自行有把握地解决这些问题，他们会在原始拉取请求中留下这条评论来寻求帮助。
当你看到这条评论时，请尝试自己打开一个回移植拉取请求来进行 backport。
技术操作方法请参见[回移植指南](./backporting-to-release-lines.md)。

如果没有人继续完成回移植，你的拉取请求可能不会被包含进任何发布中，直到从 `main` 分支切出的下一个大版本发布。
