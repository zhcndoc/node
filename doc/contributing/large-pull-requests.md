## 概述

大型拉取请求在 GitHub UI 中很难审查，有时甚至无法审查。它们很可能会长时间搁置而得不到充分审查，而即使被审查，由于审查者疲劳，审查质量通常也会更低。贡献者应避免创建大型拉取请求，除非在事实上不可避免的情况下，例如添加新的依赖项时。

本文档概述了 Node.js 项目中编写和审查大型拉取请求的政策。

## 什么情况下算作大型拉取请求

当一个拉取请求的净变更超过 **5000 行**（新增行数减去删除行数）时，就视为大型拉取请求。该阈值适用于拉取请求中的所有文件，包括 `deps/`、`test/`、`doc/`、`lib/`、`src/` 和 `tools/` 中的变更。

任何新增子系统的拉取请求，例如 `node:foo` 或 `node:foo/bar`，都会自动被视为大型拉取请求，并适用相同规则。

`deps/` 中的变更也计入此统计。依赖变更较为敏感，因为它们通常受到的审查不如第一方代码充分。

以下类别的拉取请求不受本政策约束，即使它们超过了行数阈值：

* 由自动化生成或由协作者按照标准依赖更新流程执行的常规依赖更新（例如 V8、ICU、undici、uvwasi）。
* Web Platform Tests（WPT）的导入和更新。
* 其他由机器人发起或自动化生成的拉取请求（例如许可证更新、测试夹具重新生成）。
* 仅涉及测试的重构，且不包含任何功能性变更。  
  这些拉取请求已经有既定的审查流程，因此不会从这里描述的额外要求中获益。

## 谁可以发起大型拉取请求

大型拉取请求只能由现有的
[协作者](https://github.com/nodejs/node/#current-project-team-members)发起。强烈不建议非协作者发起此类规模的拉取请求。非协作者发起的大型拉取请求将被关闭，除非该工作已在 issue 中讨论过，并且有一位协作者为其背书。

## 要求

所有大型拉取请求除标准的 [拉取请求要求](./pull-requests.md) 外，还必须满足以下要求。

### 详细的拉取请求描述

拉取请求描述必须提供足够的上下文，以便审查者理解这项变更。描述应解释：

* 这项变更的动机。
* 高层实现方法与架构。
* 考虑过哪些替代方案，以及为何被否决。
* 这项变更如何与现有子系统交互。

一份详尽的拉取请求描述就足够了。并不要求单独产出设计文档，不过贡献者也可以选择链接到 GitHub issue 或其他讨论设计形成过程的地方。

### 审查指南

拉取请求描述必须包含一份审查指南，帮助审查者浏览这项变更。审查指南应：

* 标明需要审查的关键文件和目录。
* 描述文件应当按什么顺序审查。
* 强调需要特别注意的最关键部分。
* 包含测试计划，说明该变更已如何被验证，以及审查者如何验证其行为。

### 批准要求

大型拉取请求遵循与 semver-major 变更相同的批准流程：

* 至少需要 **两位 TSC 成员批准**。
* 适用标准的 48 小时等待时间。鉴于大型拉取请求的复杂性，作者应预期并允许更长的审查周期。
* 合并前 CI 必须通过。

### 依赖变更

当大型拉取请求在 `deps/` 中新增或修改依赖时：

* 依赖变更应与拉取请求的其余部分放在 **单独的提交** 中。这样更容易独立于第一方代码变更来审查依赖更新。当拉取请求在合并时被 squash 时，依赖提交应成为携带 squash 后提交信息的那个提交，以便 `git log` 能清晰反映整体变更。
* 必须能够验证依赖的来源与完整性。  
  提供该依赖如何获取的文档，以及审查者如何复现构建产物。

## 避免大型拉取请求

贡献者应始终考虑一个大型拉取请求是否可以拆分成更小、可独立审查的拉取请求。策略包括：

* 先落地基础性的内部 API，再在其上继续构建。
* 在主功能之前先落地重构或准备性变更。

拆分系列中的每个拉取请求都应保持自包含：它应包含该部分独立成立所需的实现、测试和文档。

### 在单个拉取请求中缩短审查时长的策略

大型拉取请求可能会带来更长的审查过程，在 GitHub 上由于 UI 限制实际上难以跟踪。以下策略有助于缩短单个拉取请求中的审查时长。

* 先开 issue，以确认 core 中确实需要这样一个重大变更，从而减少与拉取请求实现无关的冗长讨论。
* 使用提案 issue、RFC、设计文档或其他形式的场合来探索高层设计和交叉关注点。
* 保持初始变更为暂定状态，以降低单个拉取请求中所需的审查彻底程度。可通过构建/运行时标志来门控过早的变更，或应用 `dont-land-*` 标签，避免在后续拉取请求中经过更充分测试和迭代之前发布初始变更。
* 将非阻塞问题（例如风格偏好）留给后续拉取请求处理，并在适当位置添加 TODO 注释。

### 特性分支与分支

对于会随时间逐步演进的极大型或高复杂度变更，例如新增一个重要子系统，贡献者应考虑使用特性分支（feature fork）。

过去这一方式已成功用于 QUIC 等子系统。

特性分支必须托管在一个 **单独的 GitHub 仓库** 中，由为该变更背书的协作者管理。该仓库可以位于
[nodejs 组织](https://github.com/nodejs)下，也可以是该背书者的个人仓库。背书者负责协调开发、管理访问权限，并确保该分支与 `main` 保持同步。

特性分支允许：

* 由多个协作者进行增量开发。
* 审查单个提交，而不是一个单一的大型差异集。
* 在开发每个阶段进行 CI 验证。
* 在分支仓库中进行独立的问题跟踪和讨论。

当工作准备就绪时，通过拉取请求最终合并到 `main` 时，仍然需要与任何其他大型拉取请求相同的批准和审查要求。

## 给审查者的指导

审查大型拉取请求会占用大量时间。审查者应：

* 在深入代码之前先阅读拉取请求描述和审查指南。
* 将审查重点放在 `lib/` 和 `src/` 的变更上，因为这些对运行时影响最大。`test/` 和 `doc/` 的变更虽然重要，但风险较低。
* 如果拉取请求合理地可以拆分成更小的部分，不要犹豫，要求作者将其拆分。
* 在可能的情况下，与其他审查者协作分担审查工作量。
